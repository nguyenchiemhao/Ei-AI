## Contradictions found while running

- 2026-09-16 — **stage 3 failed on CI run #17 and passed on #18 with no change to any test.** A gate that passes half the time is worse than one that is red. The cause was a test of mine: `revocation.service.spec.ts` built its `Principal` **once at module load**, and the TTL assertion allowed five seconds between that moment and the assertion running — comfortable locally, not on a loaded runner transforming fourteen files while Argon2id tests compete for two cores. What narrowed it was the duration rather than the message: 17 s against 18 s, near identical, so the job was not timing out, it was failing fast. The principal is now built per test and the assertion measures against the object the test just made, so any delay moves both sides together. Six consecutive local runs, green.

- 2026-09-16 — **reading the uncovered 5 % found a test that passed for a reason other than the one its name gives.** `password.service.spec.ts` had "returns false for the seed placeholder rather than throwing", and the `catch` in `verify` showed as uncovered: the placeholder is well formed enough for argon2 to **parse**, so it simply does not match and nothing is ever thrown. The catch is real — an empty string, a bcrypt hash and a truncated argon2 hash all raise `Decoding failed` — and no test reached it. Both cases are now named and asserted separately.
- 2026-09-16 — `AuthService.activeUser`, the refresh path's only look at `users`, had **no unit test at all**. The integration suite exercises it on every refresh, and that never reaches stage 3's report, so the method looked covered from the outside while the gate saw none of it. `login.dto.ts` sat at 0 % for the same shape of reason: nothing in the unit suite imported the schema the pipe enforces.

- 2026-09-16 — **a review pass over the twelve tasks found `POST /auth/logout` acting on a credential it never verified.** `revokeSession` looked the refresh cookie up by hash and revoked whatever family it named, without comparing that token's owner to the bearer token's principal — so a request carrying one user's access token and another's cookie ended the other's session. Fixed by requiring the match, and checked with two real users: Alice's logout carrying Bob's cookie returns 204, revokes Alice's own access token, and leaves Bob able to refresh.
- 2026-09-16 — **the integration suite leaked `login_attempts` rows.** `login_attempts.user_id` is `ON DELETE SET NULL`, so deleting the fixture users left their eleven rows behind for ever, in the very table the rate limit queries; fifteen orphans had already accumulated across the probes. The suite now deletes by email first, and a re-run leaves none.

- 2026-09-16 — **`T-3.1-08`'s "Done when" and the package's own proving command disagree about the eleventh attempt.** The task gives it to the rate limit; [Detail §WP-3.1](../ei-ai-phase-1-detail.md) says "lockout after 10 consecutive failures, the 11th returning `AUTH_ACCOUNT_LOCKED` (423)", and the proving command asserts 423. Ten consecutive failures trip both thresholds at the same instant, and as first written the endpoint answered 429 there — which would have **failed this package's own proving command**. Resolved by testing the lockout first. The rate limit keeps a subject of its own: ten attempts that include a success never lock, and answered 429 on attempts 11–19.

## Interpretations

- 2026-09-16 — the unit stage now echoes the tail of a failed run as a `::error::` annotation. Job logs need repository admin to download, which this session does not have, so a red stage was `Process completed with exit code 1` and nothing else. Keeping it turns a failure into something readable from the run summary by anyone.

- 2026-09-16 — **an expired access token and a revoked one both answer 401, and the first probe of `T-3.1-04` could not tell them apart.** It logged out with the token and then presented it again, so the second call failed because logout had listed it, not because it had aged — the probe would have read the same whichever mechanism fired. Re-run with a token never used and genuinely past `exp`: 401 `AUTH_TOKEN_EXPIRED`.

- 2026-09-16 — **the integration suite drives the built application over HTTP instead of booting Nest inside vitest.** Booting it there was tried and every request answered 500: vitest transpiles with esbuild, which emits no `design:paramtypes`, so `AuthController` received `undefined` for each dependency. The documented remedy is `@swc/core` plus `unplugin-swc`; running against `dist/main.js` costs no dependency at all and tests the artefact that ships, which is a rule this repository already holds. The spec makes its own fixtures with a plain `pg` client and needs no injection of its own.
- 2026-09-16 — the suite has its **own vitest config and its own CI job**, and the unit config excludes `*.integration.spec.ts`. Stage 3 has neither a database nor a Redis, and a unit stage that silently needs both is a stage that will be muted the first time it goes red for an unrelated reason.

- 2026-09-16 — **logout ends one session; reuse detection ends all of them.** Logout revokes the presented token's family and lists that one access token; it deliberately does not touch the user entry, so signing out on a laptop leaves a phone signed in. Reuse detection revokes the user because a replayed token means one of the two holders is an attacker and there is no way to tell which. Checked rather than assumed: after a logout Redis holds one `revoked:jti` key and no `revoked:user` key.
- 2026-09-16 — logout with no cookie is a success, not an error. The access token is revoked either way, and refusing to sign someone out because their cookie has already gone helps nobody.

- 2026-09-16 — **revocation by user records the moment, not a flag.** Reuse detection has to kill the access tokens already handed out, and those carry no family, so the user is the only reach there is. A plain "this user is revoked" entry would also refuse the tokens of the *next* login — the victim of a stolen token locked out of their own account for a quarter of an hour, a denial of service any thief could trigger. The entry is the revocation instant and the guard refuses only tokens issued before it; proven by logging in again the moment after the replay and being let straight back in.
- 2026-09-16 — reuse revokes the family **and** the user's live access tokens. Detail asks reuse to "force a fresh login", and a family revocation alone would leave the thief's access token working for up to fifteen minutes.

- 2026-09-16 — `Secure` on the refresh cookie is tied to `NODE_ENV` rather than set unconditionally. A Secure cookie is dropped over plain http, so a development stack would never receive one and the refresh path could not be exercised at all; production sets it.
- 2026-09-16 — `cookie-parser` is applied as Nest middleware in `AppModule` alongside the correlation id, not through `app.use` in `main.ts`, for the reason `T-3.1-01` already established: a testing module built from `AppModule` gets nothing that `main.ts` wires, and `T-3.1-12` builds one.
- 2026-09-16 — a refresh checks that the account is **still active**. The refresh token outlives the access token by hours and nothing else on that path consults `users`, so without the check a disabled account could keep minting fresh access tokens until its refresh token expired.

- 2026-09-16 — "loses its sessions **within 60 seconds**" is read as a bound the design sets, not a cache window to build. The guard consults Redis on every request, so a revocation takes effect on the next one; the other reading — cache the user's status for up to a minute — would build a delay in order to satisfy a limit on delay.
- 2026-09-16 — a disabled account is listed **by user** rather than by token, because nothing stores live access tokens and they cannot be enumerated. Every key carries a TTL of one access-token lifetime, so the list cannot grow without bound and an entry disappears once no live token could still carry it.
- 2026-09-16 — the Redis client is a provider in `adapters/cache/cache.module.ts` with no separate client file. A `redis.client.ts` would sit inside the coverage scope and be as untestable as a repository, and adding it to the exclusion list would be gaming a gate rather than passing one; `*.module.ts` is already excluded for a reason that applies here.

- 2026-09-16 — how long a lockout lasts is named nowhere: Detail and FR-65 say that one happens, not for how long. `LOCKOUT_DURATION_MS` defaults to the rate-limit window, so a locked account and a rate-limited one clear together rather than leaving a user half-blocked.
- 2026-09-16 — a locked account answers 423 while an unknown address answers 401 or 429, so the lockout does tell an attacker that an address exists. That is the design's own choice — `AUTH_ACCOUNT_LOCKED` is in §7.4 and §8 specifies a lockout message on the login screen — and it is recorded here rather than traded away in silence.

- 2026-09-16 — **a hand-made fixture hid a real defect, and the database found it.** `markRotated` writes `used_at` *and* `revoked_at`, but `refuseUnusable` tested `revoked_at` first, so a replayed token read as merely invalid rather than as reuse — which would have left FR-64's reuse detection permanently dead while every unit test stayed green. The spec's fixture set only `used_at`, a shape rotation never produces. Order corrected, and the fixture now carries both fields.
- 2026-09-16 — the refresh token is **random bytes, not a JWT**: it carries no claims, it is checked by lookup, and only its SHA-256 reaches the database, so a dump of `refresh_tokens` hands nobody a usable token. SHA-256 rather than Argon2id because this is a 256-bit secret with no guessable structure — the slow hash defends against dictionary attacks that do not apply here, and the lookup must be indexed.

- 2026-09-16 — a **rate-limited attempt is not recorded** in `login_attempts`. The window counts attempts that were actually evaluated; recording refusals would let a client hammering the endpoint extend its own block indefinitely, which punishes a confused user and changes nothing for an attacker. Proven by the row count: twelve requests, ten rows.
- 2026-09-16 — the rate limit is counted **by email, not by user id**, following `002_identity.sql`'s own comment: attempts against an address with no account must count too, or the limit answers the question "does this email exist?".

- 2026-09-16 — **a green test suite says nothing about types.** `token.service.ts` shipped a real compile error — `@nestjs/jwt` types `expiresIn` as ms's template-literal union and a plain `string` from the environment does not satisfy it — and all 44 tests passed, because vitest transpiles with esbuild and never typechecks. The container's `tsc --watch` caught it, and the running app had quietly stayed on the previous build. `ACCESS_TOKEN_TTL` now carries a `^\\d+[smhd]$` regex in the config schema so a bad value fails at boot, and the service converts it to seconds.
- 2026-09-16 — a forged or missing token is `AUTH_INVALID_CREDENTIALS` and only an aged-out one is `AUTH_TOKEN_EXPIRED`. That is the distinction a client acts on: refresh, or send the user back to the login screen.
- 2026-09-16 — the access token carries `jti` from the first issue rather than gaining it at `T-3.1-10`. The revocation list needs a per-token identity, and a claim added once tokens are in circulation is a migration.

- 2026-09-15 — `T-3.1-12`'s two scenarios run in a **job of their own beside stage 6**, on a Postgres and a Redis service container, numbered `6c` after the precedent `6b` set: the egress check rode alongside stage 6 because its natural host, stage 7, belongs to the pre-agreed cut, and identity's integration tests are in the same position. `T-5.4-01` stays in G5 where the plan put it.
- 2026-09-15 — hashing uses **`@node-rs/argon2`**, a prebuilt Rust binding with **no install script at all**, rather than `argon2` 0.41 whose `"install": "node-gyp-build"` pnpm 10 would skip in silence because the package is not in `onlyBuiltDependencies`. The algorithm is unchanged — Argon2id, which is what FR-58 and `users_password_matches_source` ask for — so what is dropped is node-gyp in the image, not a guarantee.
- 2026-09-15 — the password policy, the rate-limit window and the lockout threshold become **variables in `env.schema.ts`**, for the reason `RETRIEVAL_*` are: a security threshold is the kind of number a customer changes, and changing it should not mean editing code.
- 2026-09-15 — `T-3.1-03`'s "indistinguishable in timing" is closed by **asserting the mechanism** — an unknown account still runs one Argon2id verify against a dummy hash — together with the two responses being byte-identical. A timing comparison with a tolerance, on a shared hosted runner, is a test that fails for reasons that have nothing to do with identity.
- 2026-09-15 — the seed's `PLACEHOLDER_HASH` is deliberately not a usable credential, so the integration tests **create their own user with a real hash** rather than logging in as a seeded one. That is the WP-2.1 lesson applied before it costs anything: build the fixtures rather than borrowing whatever the database happens to hold.

## Deviations

- 2026-09-16 — **the seed can now give `admin@ei-ai.local` a real password**, and only that account, only when `SEED_ADMIN_PASSWORD` is set, and never by default: a public repository must not ship a working credential. Hashing goes through the application's own `PasswordService`, so the seed cannot drift from the parameters and the policy the running system applies. The update is its own statement rather than part of the upsert, so a later run **without** the variable leaves a good hash alone instead of resetting it. Proved across three runs: no variable → 401; variable → 200; run again without it → still 200. The password appears in no log line.
- 2026-09-16 — this adds **one manual step** to the Phase 1 milestone: an operator sets the variable before the first seed. The G1 gate line "on a clean machine — all services up, no manual step" is about services rather than credentials, and the only way to remove the step would be to publish a default password.

- 2026-09-16 — **`z.coerce.boolean()` made every flag written `false` arrive as `true`.** `.env.example` ships `TOOL_WEB_SEARCH_ENABLED=false`, and the schema read it as `true`: zod's coercion is `Boolean(string)`, so only the empty string is false. Confirmed by running the parser over `"false"`, `"0"`, `"no"` — all three produced `true`. Nothing consumes those flags yet (WP-3.5 does), so no behaviour was wrong, but the flag that keeps web search off in v1 was lying. Replaced with a `booleanFlag` helper accepting `true|false|1|0` and refusing anything else, with four tests. A defect of `T-1.1-04`, fixed here because a safety flag that contradicts its own file is not something to leave for a later package.
- 2026-09-16 — **Swagger was added at the operator's request, as scope no document names.** A grep of `docs/` finds no mention of swagger or openapi anywhere in the design, the plan or the tasks. `@nestjs/swagger` 11.4.7 (the newest that peers on Nest 11 — 12.x requires Nest 12) plus `zod-to-json-schema`, mounted at `/docs` behind `API_DOCS_ENABLED`, default **false**, turned on only by the dev `.env.example`. The document is generated from the same zod schemas `ZodValidationPipe` enforces, so the page cannot describe a contract the server does not apply.

- 2026-09-16 — **`@typescript-eslint/consistent-type-imports` is turned off for `apps/api/src/**`**, in that package's own config rather than the shared one. The rule and `emitDecoratorMetadata` cannot both hold: a class that reaches a constructor only as a parameter type looks type-only to ESLint, while Nest reads it back through `design:paramtypes`. Rewriting `auth.service.ts`'s two imports as `import type` was tried, and the application **failed to boot**, `AuthService`'s dependencies resolving to `[Function: Function]`. `apps/web` and `packages/*` keep the rule; they have no decorators. WP-2.5's `tsPreCompilationDeps` stays necessary — `import type` is now optional in `apps/api`, not absent.

- 2026-09-16 — **dropping the `node_modules` volumes is not enough; `api-dist` outlives a rebuild.** After the image rebuild the container's `apps/api/dist` still held `__probe_a.js`, `__probe_b.js`, `ci-probe.js`, `adapters/model-provider/anthropic.adapter.js` and `modules/identity/{identity.controller,users.service}.js` — compiled output of files deleted days ago, some of which never existed outside a WP-2.5 probe. Nothing was running them, but every proof taken against that container was taken against a tree that did not match the source. The volume was dropped and `T-3.1-01`'s four cases re-run on a `dist` that lists exactly what `src` contains.


- 2026-09-16 — **`*.repository.ts` joins `*.controller.ts` outside the unit coverage gate**, measured rather than assumed: with `users.repository.ts` counted the gate read **30.48 %** against a threshold of 80 %, the service itself sitting at 92.59 %. Every line of a repository is a query builder whose meaning is the SQL it produces against a real database; a unit test of one asserts that a mock was called. They are proved in the integration job instead — identity's in `6c` (`T-3.1-12`), retrieval's by the compiled-SQL and leakage specs (`T-2.3-08`, `T-2.3-09`). The gate still has a subject: it reports 92.59 %, not an empty scope.

- 2026-09-15 — **`correlation-id.interceptor.ts` became `correlation-id.middleware.ts`.** `T-3.1-01` names an interceptor, and an interceptor cannot satisfy that task's own "Done when": Nest never runs one for a path the router does not match, so `GET /nope` came back as correct RFC 7807 with `code: NOT_FOUND` and **no `X-Correlation-Id` at all**, against design §7.1's "mọi request nhận `X-Correlation-Id`". Middleware runs before routing and covers both. Found by curling the running container, not by the unit tests, which passed throughout.
- 2026-09-15 — the global filter and the middleware are registered in `AppModule` (`APP_FILTER`, `configure()`) rather than in `main.ts`. A testing module built from `AppModule` — which `T-3.1-12` will build — gets nothing that `main.ts` wires, so the integration tests would have asserted a different error shape from the one the process actually serves.

## Tradeoffs

- 2026-09-16 — the password policy is a minimum length and nothing else. FR-58 says "chính sách mật khẩu cấu hình được" and names no rule; character-class requirements are scope no task describes, and current guidance prefers length over composition. The variable is there, so a customer who wants more has somewhere to put it.
